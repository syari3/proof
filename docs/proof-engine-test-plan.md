# 推論エンジンのテスト整理計画

この文書は、問題生成器を拡張する前に、推論エンジンの挙動を安全に変更できるテスト基盤を整えるための作業計画です。

## 現状

GitHub Actions の `.github/workflows/node-tests.yml` は Node.js 20 で `tests/*.test.js` を順番に実行します。ビルドツールやパッケージマネージャーは必須ではなく、各テストは `node tests/ファイル名.test.js` で実行する構成です。

現在の主なテストファイル:

| ファイル | 主な責務 |
| --- | --- |
| `tests/proof-rules.test.js` | 推論ルール、証明探索、正例・負例、推論ステップ |
| `tests/geometry-relations.test.js` | 点の順序や幾何関係の導出 |
| `tests/theorem-catalog.test.js` | 定理カタログのスキーマ、IDの一意性、実行時ルールとの接続 |
| `tests/problem-data-format.test.js` | 問題データの形式と参照整合性 |
| `tests/problem-data-engine.test.js` | 問題データから推論用事実への変換と推論エンジン接続 |
| `tests/problem-generator.test.js` | 生成器の基本的な選別動作 |

## 現状から分かる注意点

- `proof-rules.test.js` に多くの異なる定理・推論のテストが集まっています。失敗箇所が分かりにくくなりやすいため、挙動を変えずに分野別へ分割する候補です。
- `problem-generator.test.js` は、`prove` の結果を模擬した小さなテストです。生成器の分岐は確認できますが、実際の推論エンジンと問題データを接続した統合テストの代わりにはなりません。
- テストが成功することは、数学的な正しさ全体を保証しません。ルール実装が誤っていれば、誤ったルールを使ったテストも成功する可能性があります。
- `problem-data-engine` のテストはデータ変換を対象とします。点や交点がユークリッド平面上に実在することの完全な検証とは別です。
- CI は各テストファイルを実行しますが、現状ではテストの分類やカバレッジ集計は行いません。

## 整理の方針

テストを最初から大量に書き換えず、既存のテストを基準線として維持しながら、次の順に進めます。

### 1. 既存テストの基準線を記録する

- main ブランチの GitHub Actions の最新結果を確認する。
- ローカルまたは CI で全 `tests/*.test.js` が通ることを確認する。
- テスト名と責務を一覧化し、各テストが守るべき契約を明確にする。

### 2. 推論テストを責務ごとに整理する

まずは大きな `proof-rules.test.js` の内容を、テスト挙動を変えずに次の領域へ整理することを検討します。

- 基本論理（等式の推移律、型の混同防止）
- 三角形（相似・合同・内角・二等辺三角形）
- 角（対頂角、一直線、半直線・角表記の正規化）
- 円（円周角、中心角、直径、弧、半径）
- 証明探索（前提の追跡、ステップ上限、失敗理由）

分割する場合は、既存のテストと同じ入力・期待結果を保ち、分割前後で全テストが通ることを確認します。

### 3. 各ルールに正例・負例・境界例を揃える

各推論ルールについて、可能な限り次を用意します。

- 正例: 必要な前提が揃うと結論を導く。
- 負例: 必要な前提がないと結論を導かない。
- 境界例: 頂点の重複、点の順序、異なる円の混同など、誤適用しやすいケースを拒否する。
- 根拠の検査: 各推論ステップの rule ID・前提・前提の出所が期待どおりである。

### 4. 実エンジンを使う統合テストを追加する

模擬 `prove` だけに頼らず、実際の問題データと実推論エンジンを接続したテストを追加します。

- 既存の静岡県2025年問題データを読み込み、変換結果を確認する。
- 目標が証明できる場合、成功結果と証明ステップを確認する。
- 前提をひとつ外すなどした負例で、誤った成功を返さないことを確認する。
- 未対応の条件や不正な問題データを、黙って無視せず明示的な失敗として扱う。

### 5. 生成器のテストを拡張する

- すべての候補が失敗した場合の挙動。
- 候補の検証結果と、採用された問題の対応。
- 不正なテンプレートや不足フィールドの拒否。
- 実エンジンを使って、生成候補が目標を証明できるかの確認。

## この整理作業の完了条件

- CI で既存テストがすべて成功する。
- テストファイルごとの責務が明確である。
- 各ルールの正例・負例・重要な境界例が確認できる。
- 少なくとも1つの問題データを実エンジンで通す統合テストがある。
- 「証明できた」と「図形が実際に成立する」を別の検証結果として扱い、前者だけで後者も保証したと誤認しない。

この作業では、テスト整理を理由に推論ルールの数学的な意味を変更しません。ルール自体の修正は、独立した変更としてテストを添えて行います。
